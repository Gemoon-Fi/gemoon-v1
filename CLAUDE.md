## Конвенции кода
- Стиль наименований (i_immutable, s_storage, _private, CamelCase для структур/событий и т.п. — зафиксировать свой стандарт)
- NatSpec обязателен для публичных/внешних функций
- Явно указывать видимость, порядок: modifiers → checks → effects → interactions (CEI)
- Кастомные ошибки (`error X()`) вместо `require(..., "string")`
- Явные версии solitidy, без диапазонов в проде

## Безопасность (критично для крипто-проекта)
- Все внешние вызовы — после эффектов (защита от reentrancy), либо явный `nonReentrant`
- Проверка checks-effects-interactions в каждом PR
- Access control — явно указать паттерн (Ownable2Step, AccessControl, роли)
- Не доверять возвращаемым значениям токенов без проверки (safeTransfer/safeERC20)
- Оверфлоу/андерфлоу — 0.8.x встроенная защита, но помнить про `unchecked` блоки
- Явно фиксировать инварианты для invariant-тестов
- Любое изменение в контрактах, работающих с деньгами — требует теста на fuzz/invariant, не только happy path
- Не запускать/не предлагать деплой в mainnet без явного запроса пользователя (это action с реальными деньгами)

## Тестирование
- Обязательный минимум для новых функций: unit + хотя бы один fuzz-тест на инварианты
- Fork-тесты — с какого RPC/блока, где хранить env (не коммитить ключи/RPC с секретами)
- Формат тестовых имен: `test_Function_Scenario_ExpectedResult`

## Что НЕ делать
- Не хардкодить приватные ключи, mnemonic, RPC-урлы с API-ключами в коде/скриптах
- Не менять версии зависимостей в `lib/` без явного запроса
- Не убирать существующие проверки безопасности "для упрощения теста"
- Не публиковать код в публичные объяснители/примеры, если контракт непубличный
